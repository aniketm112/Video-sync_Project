# Expo Dependency Audit — final pass (post-EAS-removal)

Date: 2026-10-07 · Commit reviewed: `830825f` · Verdict: **keep the Expo SDK; remove nothing**

Earlier cleanup already removed every *user-facing* Expo artifact: the EAS
configuration (`eas.json`, `extra.eas`), Expo CLI scripts, and all Expo/EAS
documentation. What remains is the Expo **SDK runtime layer**, and every piece
of it is load-bearing for the shipped Android APK. This document records what
each remaining package does, whether a standard React Native equivalent could
replace it, and why replacement was rejected.

## Summary verdict

| Dependency | What it provides here | RN-native replacement possible? | Decision |
|---|---|---|---|
| `expo` (~54.0.33) | Core runtime: module autolinking infra, `expo/scripts/resolveAppEntry` (wired into `android/app/build.gradle`), version catalog for Gradle, `expo-font`/`expo-constants` transitively | Not independently — it is the glue the committed native project is generated around | **Keep** |
| `expo-router` (~6.0.23) | The entire navigation layer: file-based routes (`app/`), `Stack` + `Stack.Protected` auth guards, `Tabs`, `useRouter`, `useLocalSearchParams`, deep links (`videosyncapp://`) | Yes, but only by rewriting all 8 screens onto React Navigation directly | **Keep** (rewrite = high regression risk, zero end-user benefit) |
| `expo-constants` (~18.0.13) | Hard dependency of `expo-router` (route config/manifest access). Not imported by app code | No — it is a router dependency | **Keep** (transitive) |
| `expo-status-bar` (~3.0.9) | `<StatusBar style="light">` in `app/_layout.tsx` | Trivially (`react-native` `StatusBar`) | **Keep** (trivial surface, no risk) |
| `expo-image` (~3.0.11) | `Image` in the 3 video-list components (thumbnails, caching, fade-in) | Yes (`react-native` `Image`) | **Keep** (drop-in swap gains nothing; it is compiled into the APK already) |
| `expo-haptics` (~15.0.8) | Tab-press haptics in `components/haptic-tab.tsx` | Yes (`VibrationAPI` / `ReactNativeHapticFeedback`) | **Keep** — see "dead files" below |

Entry point: `package.json` `"main": "expo-router/entry"` — the router mounts
the app from the `app/` directory; the bundle the APK embeds starts there.

## Why navigation stays on expo-router

`expo-router` is not a thin wrapper — it is the app's navigation backbone and
the `app/` directory *is* the route table:

- `app/_layout.tsx` — root `Stack` with `Stack.Protected` guards that switch
  the entire tree between `(auth)` and `(tabs)`/`video/[id]` on auth state.
  This centralized guard is the fix for the logout navigation-state crash
  ("Maximum update depth exceeded"); per-screen `<Redirect>` guards caused it.
- `app/(tabs)/_layout.tsx` — `Tabs` (bottom tab navigator).
- `app/(auth)/login.tsx`, `app/(auth)/signup.tsx`, `app/index.tsx` — `useRouter`.
- `app/video/[id].tsx` — `useLocalSearchParams` for the video id + deep-link entry.
- `components/external-link.tsx` — router `Link` (currently unreferenced).

A migration would replace all of this with hand-written React Navigation
`NavigationContainer` + `native-stack` + `bottom-tabs` and a hand-rolled auth
gate — i.e. re-implementing what the router does, in a codebase where the
guarded flow is the core product behavior. The risk/benefit is upside-down:
the router is bundled into the APK already, adds nothing users must install,
and works.

## Why the environment-variable mechanism stays

`lib/firebase.ts` reads the Firebase web config from `EXPO_PUBLIC_*`
environment variables (7 vars), sanitizing pasted values with `cleanEnv()`,
and `lib/auth.tsx` surfaces misconfiguration as a user-readable error. Expo's
Metro transform inlines `process.env.EXPO_PUBLIC_*` at bundle time — which is
exactly why the released APK needs **no** user Firebase setup. Any replacement
(React Native Config, `--define` constants) would be a lateral move that
re-touches the most sensitive file in the app for no functional gain.

## Why the Gradle build itself depends on Expo

The committed native project is Expo prebuild output and its build is driven by
Expo tooling (`android/settings.gradle`):

- `expo-modules-autolinking` resolves all native modules and supplies the
  React Native Gradle plugin (`useExpoModules`, `useExpoVersionCatalog`,
  `includeBuild(...reactNativeGradlePlugin)`).
- `android/build.gradle` applies `expo-root-project`.
- `android/app/build.gradle` resolves the JS entry via
  `require('expo/scripts/resolveAppEntry')`.
- `MainActivity.kt` imports `expo.modules.ReactActivityDelegateWrapper` and
  `expo.modules.splashscreen.SplashScreenManager` (splash-screen plugin hook).
- `gradle.properties` carries Expo build flags (`expo.gif.enabled`,
  `expo.webp.*`, `expo.edgeToEdgeEnabled`, …).

Stripping Expo here means regenerating a plain React Native Android project
and re-deriving every manifest/theme/resource — a full native re-setup to reach
exactly the APK that already exists.

## Dead template files (left in place, harmless)

Three Expo-template components exist in `components/` but are **imported by
nothing** (verified by searching for every import path):

- `components/haptic-tab.tsx` (expo-haptics)
- `components/external-link.tsx` (expo-router `Link`, expo-web-browser)
- `components/ui/collapsible.tsx` (uses `IconSymbol`)

They are tree-shaken out of the release bundle and contribute nothing to the
APK. They were left untouched in this pass only because this audit is a
no-risk documentation pass; deleting them later is cosmetic and safe.

## What was explicitly rejected

- **Removing Expo packages "to look Expo-free".** The standalone APK already
  contains everything; package.json provenance changes nothing for users.
  Removal risks: auth-persistence regression, navigation crash regression,
  broken Gradle autolinking, broken env inlining — for zero user benefit.
- **Swapping `expo-image` → RN `Image` or `expo-status-bar` → RN `StatusBar`.**
  Possible, but each swap means a rebuild + full re-verification of every
  screen for purely cosmetic provenance. Rejected as risk without reward.

## Bottom line

The app ships as a fully standalone Android APK (no Expo Go, no Expo CLI, no
Node, no Firebase setup, no source). The Expo SDK inside the repository is the
runtime that produces that APK. Keeping it is the correct engineering call;
"Expo-free" was and is the wrong goal — "Expo-tooling-free for users" is
achieved and is what matters.
